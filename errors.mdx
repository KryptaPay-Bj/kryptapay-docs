title: "Errors"

---

Every error uses the same envelope. Branch on `error.code` — it is stable. `error.message` is for humans and may change.

```json
{
  "ok": false,
  "error": {
    "code": "amount_decimal_not_allowed",
    "message": "Montant décimal non autorisé (montant entier requis)."
  }
}
```

<Note>
  Some `message` values are in French. Never parse or display them as-is to end users — map `code` to your own wording instead.
</Note>

## HTTP statuses

| Status | Meaning | Retry? |
| --- | --- | --- |
| `200` / `201` | Success / resource created | — |
| `400` | Malformed request, e.g. invalid JSON | No — fix the request |
| `401` | Missing, invalid or expired API key | No — check the key |
| `403` | Key lacks a scope, or the account isn't KYB-approved | No |
| `404` | Resource not found | No |
| `409` | Conflict: wrong state for the action, or a duplicate payout | No |
| `413` | Request body larger than 1 MB | No |
| `422` | Validation error or business rule (see codes below) | No — fix the request |
| `429` | Rate limit exceeded | Yes — after `retry-after` seconds |
| `5xx` | Server or upstream error | Yes — with backoff |

## Validation errors

A body that fails validation (missing or invalid field, wrong type, unmet cross-field rule) returns `422` with `code: "validation_error"`. `message` names the first failing field; `details.fieldErrors` lists every failing field by path.

```json
{
  "ok": false,
  "error": {
    "code": "validation_error",
    "message": "customer.msisdn: customer.msisdn is required for mobile money network MTN_BJ",
    "details": {
      "formErrors": [],
      "fieldErrors": {
        "customer.msisdn": ["customer.msisdn is required for mobile money network MTN_BJ"]
      }
    }
  }
}
```

## Error codes

| Code | Status | What happened | What to do |
| --- | --- | --- | --- |
| `unauthorized` | 401 | The API key is missing, invalid, revoked or expired. | Check the key and environment. |
| `insufficient_scope` | 403 | The key doesn't have the scope this action needs. | Use a key with the right [scope](/authentication#scopes). |
| `kyb_required` | 403 | The organization isn't KYB-approved, or is suspended or closed. | Complete KYB, or contact support. |
| `not_found` | 404 | The resource doesn't exist or belongs to another account. | Check the id or reference. |
| `bad_status` | 409 (422 on confirm-otp) | The resource can't change state, e.g. cancelling a payout that is already processing. | Fetch it to see its current status. |
| `validation_error` | 422 | The body failed validation — see `details.fieldErrors`. | Fix the listed fields. |
| `amount_below_min` | 422 | Below the Mobile Money minimum for this currency, given in `details.min`. | Increase the amount. |
| `amount_above_max` | 422 | Above the per-transaction maximum for this network, given in `details.max` (Ghana: 10,000 GHS). | Split the amount into several payments. |
| `amount_decimal_not_allowed` | 422 | Decimal amount for a zero-decimal currency (XOF, XAF, NGN). | Send an integer amount. |
| `network_unavailable` | 422 | The operator is temporarily under maintenance. | Retry later or use another network. |
| `no_wallet` | 422 | No active wallet in this currency. | Contact support to open one. |
| `insufficient_funds` | 422 | Not enough available balance for the payout. | Top up the wallet and retry. |
| `insufficient_funds_with_fee` | 422 | The balance doesn't cover amount + fee. | Top up, or use [Quote a fee](/api-reference/fees/quote) to get `maxSendable`. |
| `funds_not_yet_available` | 422 | The payout needs funds from a conversion into a fiat currency made less than 24 hours ago. | Send up to `details.withdrawable` now, or retry after `details.availableAt`. See [Funds from a recent conversion](/payouts#funds-from-a-recent-conversion). |
| `limit_exceeded` | 422 | Per-transaction, daily or monthly limit reached. | Reduce the amount or ask support to raise the limit. |
| `duplicate_within_window` | 409 | Same recipient, amount, currency and network within 60 seconds under a different or missing `Idempotency-Key`. | Check `details.existingReference`; retry with the original `Idempotency-Key` instead. |
| `counterparty_required` | 422 | A `BANK_EUR` / `BANK_USD` payout was sent without `counterpartyId`. | Save the recipient as a [beneficiary](/beneficiaries) and pass its id. |
| `counterparty_not_found` | 422 | `counterpartyId` doesn't match a beneficiary of your account. | Check the id. |
| `counterparty_not_approved` | 422 | The beneficiary is still under review, or was rejected. | Wait for approval, or fix the beneficiary. |
| `counterparty_blacklisted` | 422 | You blacklisted this beneficiary. | Remove it from the blacklist if the payout is intended. |
| `incomplete_counterparty_docs` | 422 | The company beneficiary is missing its trade register extract or manager's ID. | Add the documents to the beneficiary. |
| `recipient_account_mismatch` | 422 | The `iban` / `accountNumber` sent isn't the beneficiary's saved account in this currency. | Send the saved account, or update the beneficiary. |
| `email_used_by_other_entity_type` | 422 | The beneficiary's email is already used to verify an individual (for a company) or a company (for an individual). | Give the beneficiary another email. |
| `verification_request_rejected` | 422 | Our payment partner refused to create the beneficiary's verification. | Check the beneficiary's name and email, or contact support. |
| `beneficiary_verification_pending` | 422 | The beneficiary hasn't completed identity verification, required for `EUR` / `USD` bank payouts. | [Resend the verification link](/beneficiaries#3-resend-the-link). |
| `otp_failed` | 422 | Wrong payin code, or the operator refused the payment. | Let the customer generate a new code and retry. |
| `otp_unsupported` | 422 | The payin doesn't use a confirmation code. | Don't call confirm-otp unless `otpRequired` was true. |
| `rate_limited` | 429 | Too many requests for this key. | Wait `retry-after` seconds, then retry. |
| `payin_unavailable` | 502 | The operator couldn't start the payin. | Retry with backoff, or use another network. |
| `internal` | 500 | Unexpected server error. | Retry later; contact support if it persists. |

## Failure codes

A payin or payout can be accepted and then fail later, once the operator answers. It then moves to `FAILED` and carries a `failureCode` and a human-readable `failureReason`:

- on [Get a payin](/api-reference/payins/get) and [Get a payout](/api-reference/payouts/get) as `failureCode` / `failureReason`;
- in `PAYIN_FAILED` and `PAYOUT_FAILED` [webhooks](/webhooks) as `failure_code` / `failure_reason`.

Like `error.code`, branch on `failureCode`, never on the reason text.

### Error or failure?

| | Error code | Failure code |
| --- | --- | --- |
| When | The request is refused | The request was accepted, the payment failed afterwards |
| Payment created | No | Yes, with status `FAILED` |
| Where you get it | `error.code` in the HTTP response (4xx/5xx) | `failureCode` on the payin or payout, `failure_code` in the webhook |
| Funds | Nothing reserved | Reserved payout funds are released |

The same kind of problem can come either way, depending on when it happens. Handle both: the error when you create the payment, and the `FAILED` status or webhook afterwards. Some codes look alike but mean different things:

| Error code | Failure code | Difference |
| --- | --- | --- |
| `insufficient_funds` | `payer_insufficient_balance` | Your wallet balance vs. the customer's Mobile Money balance |
| `otp_failed` | `payer_declined` | Wrong confirmation code vs. the customer refused on their phone |
| `payin_unavailable` / `network_unavailable` | `provider_error` | The operator couldn't start the payment vs. the operator returned an error afterwards |

The two lists never share a code.

| `failureCode` | Applies to | What happened | What to do |
| --- | --- | --- | --- |
| `payer_insufficient_balance` | Payin | The customer's Mobile Money balance is too low. | Ask the customer to top up, then create a new payin. |
| `payer_declined` | Payin | The customer refused the payment. | Create a new payin if the customer wants to retry. |
| `payer_timeout` | Payin | The customer didn't approve the payment in time. | Create a new payin. |
| `invalid_account` | Payin, payout | The number or account doesn't exist. | Check the number or account details. |
| `recipient_limit_exceeded` | Payout | The recipient's account has reached its limit. | Send a smaller amount, or retry later. |
| `provider_error` | Payin, payout | The operator returned an error, or didn't say why the payment failed. | Retry later, or use another network. |

<Warning>
  How precise the code is depends on what the operator reports: some operators say why a payment failed, others don't. When they don't, you get `provider_error`, in sandbox and in production alike. Always handle `provider_error` as a generic failure.

  `failureCode` is `null` on payments that failed before failure codes were introduced, and on payouts rejected by KryptaPay's review — `failureReason` explains why.
</Warning>

To trigger each failure code in sandbox, use the [sandbox test numbers](/testing).

## Retrying safely

- Retry only on `429` and `5xx`, with exponential backoff (for example 1 s, 2 s, 4 s… capped at 1 minute).
- For payouts and conversions, always resend the **same** `Idempotency-Key` so a retry can never move money twice. See [Idempotency](/requests-and-responses#idempotency).
- If a request times out, don't assume it failed: look the resource up (or rely on its webhook) before trying again.
- When contacting support about an error, include the response's `X-Request-Id` header.
